## Known gotchas (read before touching these areas again)

- **Amplify env vars only reach the build shell, never the deployed runtime** (Route Handlers, ISR revalidation past the first window) — [AWS docs](https://docs.aws.amazon.com/amplify/latest/userguide/ssr-environment-variables.html). Any new server-only env var must be added to `amplify.yml`'s `env | grep -e VARNAME >> .env.production` line, not just set on the Amplify app, or it silently reads `undefined` at request time while working fine at build time.
- **`iamServiceRoleArn` ≠ the SSR Compute role.** The former grants nothing to the deployed Lambda. Use `--compute-role-arn` (CLI) / App settings → IAM roles → Compute role (Console) — [docs](https://docs.aws.amazon.com/amplify/latest/userguide/amplify-SSR-compute-role.md). Both are currently set to the same role, `portfolio-next-amplify-ses`.
- **GitHub OIDC `sub` claim on this account uses the ID-qualified format** — `repo:derikschneider@239501139/portfolio-next@1307245039:ref:refs/heads/main`, not the plain form most examples show. The IAM trust-policy condition (in AWS, not this repo) must match that exact form or `AssumeRoleWithWebIdentity` fails with a generic "Not authorized." Debug by decoding the actual token (`curl` `$ACTIONS_ID_TOKEN_REQUEST_URL`, base64-decode the JWT payload) rather than assuming the claim shape.
- **Editing Contentful content alone doesn't update the live site** until the next ISR revalidation (1h) or a fresh deploy — force an Amplify redeploy if it needs to be live immediately.
- **Use `text-fg-NN` utilities (`globals.css`), never `text-foreground/NN`,** for dimmed text — the opacity syntax mixes toward transparent and compositing against the animated background makes it transition unevenly against opaque text.
- **The theme-color transition rule lives in `@layer base` on purpose** — unlayered CSS unconditionally wins the whole `transition-property` cascade over component-level transitions. If a new hover/enter animation doesn't seem to animate, check `getComputedStyle(el).transitionProperty` in devtools before assuming the component code is wrong.
- **Font-stack order is Helvetica-first on purpose — don't "fix" it.** `--font-display`/`--font-sans` are `Helvetica, "Helvetica Neue", var(--font-space-grotesk), sans-serif`. Derik's call (2026-08-04): Helvetica should win where it's genuinely installed (macOS), with Space Grotesk only picking up where it isn't. **The known consequence is that Windows never reaches Space Grotesk** — the OS substitutes the missing "Helvetica" with Arial, so the browser resolves the first entry and stops. Windows visitors get Arial. That same mechanism was previously an actual bug (Space Grotesk never rendered anywhere; fixed in f6aae95 by putting the web font first), so this looks identical to that regression in a diff — it isn't. Verify font changes against the actually-served CSS bundle, not the source file, since this class of thing looks correct in source either way.
- SES: domain identity `work.derikschneider.com` (DKIM via Cloudflare), sends to one verified recipient, stays in sandbox mode deliberately (sandbox restrictions never bind with a single pre-verified recipient).
- Custom domain: two Cloudflare CNAMEs, both DNS-only (not proxied) — required for ACM validation and CloudFront routing. Doesn't touch the apex `derikschneider.com` A records (those serve `vite-lit-1`).

## Key decisions (why, not just what)

- **Pinned to Next.js 15.5.x, not 16.** AWS Amplify Hosting's official Next.js support currently tops out at v15 — v16 adapter support was still in progress as of mid-2026 (tracked in `aws-amplify/amplify-js` issues #14600 / #14614). Re-verify Amplify's supported version before ever bumping past 15.x.
- **Hosting: AWS Amplify Hosting**, not S3+CloudFront. Amplify has no *verified* Next.js adapter per Next.js's own docs (only Vercel and Bun currently do — see `node_modules/next/dist/docs/01-app/03-api-reference/07-adapters/`), but it's AWS's own long-standing SSR/ISR-capable integration, and Capital One is a famous AWS-native, all-in shop, so leaning into a real AWS service (not a workaround) is the credible choice.
- **CI/CD split across two workflows on purpose:** `.github/workflows/ci.yml` owns lint/typecheck/test/build as required PR checks. `.github/workflows/deploy.yml` authenticates to AWS via **GitHub OIDC** (no stored AWS keys) and calls `aws amplify start-job --job-type RELEASE` on push to `main`. Amplify's own git-triggered auto-build is disabled so GitHub Actions is the sole deploy trigger — this is the actual "CI/CD to AWS" story, not just Amplify's default webhook.
- **Contentful-driven pages use classic ISR** (`export const revalidate`), not Next 16's newer opt-in Cache Components model (`cacheComponents: true`). Deliberate: avoid stacking a brand-new caching primitive on top of an already-unverified Amplify adapter.
- **Contact form** is a custom Route Handler → AWS SES (`@aws-sdk/client-sesv2`), not a form SaaS — more AWS surface area to speak to.
- **Domain:** `work.derikschneider.com` — a subdomain, kept separate from the root creative-brand site.
